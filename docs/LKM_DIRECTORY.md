# LKM Directory (Platform Admin → LKM Directory)

Our copy ("snapshot") of the Lembaga Kaunselor Malaysia register. Counselor registration is checked against it (design decision C1: a match is required, otherwise no account). Sample data is made up — not a copy of the real register (design doc, 2.2).

**First step — built:**
- List (`/platform/lkm-directory`): search by name, KB number or email; filters for status (Aktif / Tidak Aktif / Digantung), PA (valid / expiring within 30 days / expired — whole days, valid until today still counts), state, and "registered on MyKaunsel or not"; paginated (15). Everything is validated on the server and lives in the URL.
- **A permanent "Simulated data" banner** (cannot be closed): the records are made for this system, not copied from the real register; a link to the official LKM directory needs an MoU (Future Work). Four summary tiles above the list (records, active, PA expired, on MyKaunsel) count the whole directory and link to the matching filter.
- **Sort**: name (default), KB number, or PA expiring first (already-expired records come first). The sort is in the URL, is not counted as a filter, and every order ends with `id` so pages never shuffle.
- The "On MyKaunsel" column names the linked counselor(s) with a link to the Counselors page, or says "Not linked". The link is still worked out from the KB number (no extra column). Expired rows get a red left edge; the status badge has an icon as well as a colour.
- **Checks while typing** (a help only; the server checks again on save): KB/PA numbers are made upper-case and checked for `KB`/`PA` + 5 digits, "valid until" before "valid from" is flagged, a KB number already in the directory is shown in red, and a PA number another record already has is shown in amber (saving is still allowed; the saved message repeats the note). They use `GET /platform/lkm-directory/lookup` (Platform Admin only, throttled, accepts only well-formed KB/PA numbers).
- Add a record and change a record (the same form on the record page). KB number: `KB` + 5 digits, unique; PA number `PA` + 5 digits (typed in lower case is accepted); valid-until not before valid-from; email, city, state optional. Name is compared exactly by registration, so the form says so.
- **The KB number cannot be changed** after a record exists (counselors are matched by it). A wrong KB number: mark that record "Tidak Aktif" and add a new record with the right number.
- **Records are never deleted** (there is no delete route, and no `lkm.record_deleted` audit action; the future CSV import will only create or update, never delete). A counselor who is no longer registered is marked "Tidak Aktif" or "Digantung": only "Aktif" counts as registered, so they can no longer register or be approved/reactivated, while the record stays for accounts that already refer to it.
- Decisions kept from the first build (they differ from the original checklist on purpose): separate pages instead of modals, 15 rows per page, and editing a record that a counselor is linked to is allowed (the page says the counselor's account is not changed automatically).
- Every add / change is written with its audit entry in one transaction (`lkm.record_created`, `lkm.record_updated` with only the changed fields, old → new).
- The record page shows the MyKaunsel counselors registered with that KB number (with how well they match: "Matches LKM" etc., linking to their page) and the record's history. Changes are **not** copied into counselor accounts; they show in the next LKM check (application review, approval, reactivation).
- Counselors page ↔ LKM Directory: links both ways; the audit log links LKM entries back to the record.

**CSV import and export — built** (`/platform/lkm-directory/import`, `.../export`; Platform Admin only):
- **Template**: the nine columns (`kb_number, pa_number, full_name, status, pa_valid_from, pa_valid_until` required; `email, city, state` optional) and one made-up example row (KB99999 — delete it before importing).
- **Mandatory box**, ticked at the upload AND again before the import: "This file contains simulated or test records only, not copied from the real LKM directory." The server refuses without it; the buttons are also disabled until it is ticked. This is the PDPA control: the import is for the made-up dataset only.
- **Limits**: UTF-8 CSV with commas, 2 MB, 5,000 rows (`config/lkm.php`). A file is turned down as a whole, with the reason, when it is empty, not UTF-8, semicolon-separated, has a missing / unknown / repeated column, or is too big. A byte-order mark, `KB Number` / `PA-Number` style headings, blank lines, quoted commas and quoted line breaks are fine.
- **Preview first, nothing written**: "42 rows: 39 new, 3 updates, 0 errors" (plus "unchanged" when a row is already exactly like the directory). Lists the records that would change (which columns, and whether a counselor account is linked) and every problem by row number, column and reason; the error report downloads as CSV (no row content, only row / KB / column / problem).
- **Matching**: by KB number (upper-cased and trimmed; PA number upper-cased; status accepted in any letter case). A KB that is in the directory is **updated** (everything except the KB number, linked records too — their accounts are not changed automatically, the preview says so); a new KB is **created**. Never deletes. The same KB twice in one file: the first counts, later rows are errors. An optional column that is missing from the file keeps the record's value; an empty cell in a column that is there clears it.
- **Saving**: all rows in one database transaction with the audit entry (`lkm.records_imported`: counts only — rows, new, updated, unchanged, skipped, linked_updated — never the rows), or nothing. If the file has errors the admin must choose "Import valid rows only". If the directory changed since the preview, nothing is saved until the new numbers have been shown. A failure while saving saves nothing and keeps the file for another try.
- **The waiting file** lives on the private `lkm_imports` disk under a random name, only for the admin who uploaded it, and is deleted on import, on cancel, when a new file replaces it, and after 24 hours (swept on the next upload).
- **Export** (`lkm.records_exported`, counts and filters only): the records the list shows (same search and filters, up to 10,000), in the same columns as an import file so it can be edited and imported again. Every cell that a spreadsheet could read as a formula (starting with `=`, `+`, `-`, `@`) gets a leading apostrophe; the error report and the template go through the same guard.

**Review requests — built** (`/platform/lkm-directory/reviews`, the "Review Requests" tab next to "Directory", with the number waiting; Platform Admin only). A counselor whose practising certificate was renewed asks for their LKM record to be checked again, with evidence.
- **Sub-tabs** Pending (longest wait first) and Resolved. A pending card shows the counselor (linked to the Counselors page), KB number, when it was asked and how long it has waited, and a table "Current in system → Claimed by counselor" for PA valid until (and PA number / name when those are claimed too). The "current" value is the LKM record as it is now. Empty state: "No pending review requests from counselors."
- **Evidence is required** (a PDF, JPG or PNG up to 5 MB, checked by its content as well as its name). It is kept on the private `lkm_review_evidence` disk under a random name. **No public URL:** "View evidence" goes to an authenticated route that hands out a signed link valid for 2 minutes and tied to that one admin; every time the file is really served it is written to the audit log (`lkm.evidence_viewed`; a PDF viewer asking for pieces counts once). Served with `nosniff`, no-store and a strict content security policy.
- **Update record**: a window with the claimed values as the starting point, which the admin can adjust (only fields the counselor claimed can be set). It lists what will change before confirming. The date must be a real date that has not passed and not before the certificate's own start date, and something must actually change. The LKM record is updated (`lkm.record_updated`, so the record's own history shows it), the counselor's profile takes the new PA date from the record (only from an active record, never the PA number or the name, same as everywhere), and the counselor is emailed the new date.
- **A suspended counselor stays suspended.** The request only refreshes the profile; lifting a suspension (for example one made by the daily PA check) stays a separate decision on the Counselors page. The email says so, the message to the admin says so, and the Resolved card links to "Reactivate on the Counselors page".
- **Reject**: a reason of at least 10 characters (quick reasons: evidence unclear, dates do not match, evidence needed) is emailed to the counselor; the record is untouched. The counselor can ask again.
- **Audit** (target = the counselor, so it also shows in their activity on the Counselors page): `lkm.review_requested`, `lkm.review_approved` (with the changes and whether they are still suspended), `lkm.review_rejected` (with the reason), `lkm.evidence_viewed`, `lkm.evidence_purged`. Each decision's audit entries are written in the same transaction as the change (all or nothing); the emails are queued and sent only after the commit (a queue worker must be running). Another admin deciding first gives "already approved/rejected by …" and nothing happens twice. (`lkm.review_resolved` was replaced by approved / rejected.)
- **One pending request per counselor**, in the service and by a unique index in the database (`pending_for`).
- **Retention**: `php artisan lkm:purge-review-evidence` (daily 02:45, `--dry-run` to look) deletes the evidence 30 days after the decision (`config/lkm.php` → `review.evidence_retention_days`). The database change and a system audit entry are saved first, then the file is deleted. The request row stays, with "Evidence removed". A pending request is never touched.
- **Counts for the Dashboard**: `LkmReviewRequest::pendingCount()` (and the `pending()` scope) are ready; the Dashboard card / "Needs your attention" item is not connected yet. The Counselors page already shows a notice with a link when a counselor has a request waiting.
- **Sample data**: `LkmReviewRequestSeeder` (part of `db:seed`): two pending (one counselor suspended by the system because the PA expired), one rejected, one approved, and one approved whose evidence was already removed.
- **Not built:** the counselor's own "Request re-verification" button (the counselor portal does not exist yet). `LkmReviewService::request()` is what it will call: it checks the claim and the evidence and writes the request and its audit entry. Until then requests exist only as sample data. Admins are not notified of a new request by email; the tab count is enough for now (add an Account notification toggle only if wanted).
- **Not done on purpose:** an `updated_by` column on the LKM record (the audit log already says who changed what), and no change to who may edit a record that counselors refer to.

Automatic import from LKM is Future Work (needs an MoU/API).
